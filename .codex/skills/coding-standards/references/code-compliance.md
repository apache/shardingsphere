# Strict Coding Standards Compliance

## Audit Targets

Audit every production, test, grammar, configuration, workflow, and other file in scope that a written coding standard explicitly covers. Do not assume that only Java files are subject to the audit.

Determine the files to check from the objects, paths, and purposes explicitly governed by each rule. Applicable standards may cover Java, G4, GitHub Workflow files, configuration files, or any other file category named by a written repository rule.

Discover files from their actual paths and purposes rather than only from the extensions expected for compliant files. For example, a rule requiring GitHub Workflow files to use `.yml` still requires enumerating files with `.yaml` or other extensions in the workflow directory.

Exclude a file only when ignore rules, repository instructions, or generation configuration proves that it is a developer-local file, generated code, a build artifact, or externally copied content. Mark an in-scope file with no applicable written coding standard as `Not constrained by written standards`; do not count it as compliant and do not invent a rule for it.

## Enumerate Applicable Rules

Before checking physical lines, read `CODE_OF_CONDUCT.md`, every `AGENTS.md` that applies to the target path, Checkstyle, Spotless, and any other standard explicitly referenced for the target category.

For each rule, record its source, exact requirement, constrained files, exceptions, and inspection method. Classify the rule as mandatory, prohibited, conditional, or advisory.

## Determine Applicability

Complete the following checks before classifying existing code as non-compliant:

1. Read the exact requirement, including required actions, prohibited actions, allowed forms, exceptions, and verification methods. Do not add prohibitions based on personal preference.
2. Determine whether the rule governs all existing code or only code that is new, modified, touched, submitted, or generated by Codex.
3. Confirm that the current file and its state are within the rule's scope. A rule that only guides future changes cannot prove that untouched existing code is non-compliant.
4. Check whether a repository-level or parent rule explicitly permits the current form or another compliant form. Do not use a narrower preference to override an existing permission.
5. Do not report a compliance violation when the rule does not apply to the current file.

`AGENTS.md` determines how to conduct the audit. Use an `AGENTS.md` rule as evidence against existing source only when the rule explicitly constrains existing source rather than only code created, modified, or delivered by Codex.

Mandatory and prohibited rules directly determine compliance. A conditional rule establishes a violation only when its condition is satisfied and no written exception permits the current form. Development philosophy and general clean-code principles are not independently enforceable compliance rules unless another written standard states an exact requirement.

When material rules conflict or their applicability cannot be determined, do not choose the stricter interpretation. Mark the affected files or checks as `Blocked`.

## Inspect Every File and Physical Line

Run `scripts/build_audit_inventory.py` to create the initial inventory.

1. Associate every in-scope file with its applicable rules or mark it as `Not constrained by written standards`.
2. Check every physical line of each constrained text file, including licenses, blank lines, comments, declarations, and bodies. Also check filenames, directories, member order, cross-file consistency, and other requirements that cannot be expressed by a single line.
3. For Java, include production and test source, top-level and nested classes, interfaces, enums, records, annotation types, `package-info.java`, and `module-info.java`.
4. Record each file as `Pending`, `Checked`, `Blocked`, or `Not constrained by written standards`, together with its checked line count and rules. Do not sample files, infer one file from another, or substitute representative files for complete coverage.
5. Rebuild the affected inventory when target content changes during the audit. Do not use a stale inventory for the compliance conclusion.

## Use Checkers and Manual Inspection

Run Checkstyle, Spotless, and other repository checkers only in check mode. Do not run `apply`, `format`, or another correction mode.

When a checker may modify the working tree, run it only in an isolated copy outside the working tree. The isolated copy must contain the current audited files and rule configuration, not only `HEAD` content or formatted content, and the check must not install dependencies or access the network.

If a required checker cannot be run safely and no other method can determine the result, mark the affected rules as `Blocked`.

A passing checker proves only the rules that the checker actually covers. Continue physical-line inspection for naming, ordering, conditional, semantic, and file-category rules that the tool does not cover. Do not replace a required checker with manual inspection when the checker determines strict formatting compliance.

## Violations and Conclusions

An existing-code violation of an applicable written standard is sufficient to report non-compliance. Do not require an additional semantic consequence and do not assign a severity label.

For every violation, report the rule source, exact requirement, applicability conditions, exceptions, all violating locations, the way each location violates the rule, and the minimum correction. Violations with the same rule and correction may be grouped only when every violating location is listed rather than sampled.

Use exactly one compliance conclusion:

- `Strictly compliant`: At least one constrained file exists, every constrained file and physical line was checked, every applicable rule was verified, and no violation was found.
- `Non-compliant`: At least one explicit violation of an applicable written standard was confirmed.
- `Partial audit`: At least one file, physical line, applicable rule, or required verification was unchecked or blocked. Confirmed violations may also be reported, but the remainder of the scope must not be described as compliant.
- `Not applicable`: No file in scope is constrained by an applicable written coding standard. Do not describe this result as `Strictly compliant`.

Report the audit scope, conclusion, checked and total files, checked physical lines, checked and total applicable rules, files not constrained by written standards, excluded files, and blocked checks. Append the uncovered scope and missing information for a `Partial audit` result.
